**Luồng xử lý của API `POST /api/v1/auth/register`**  

---

## 1. Endpoint và tham số

```java
@PostMapping("/register")
public ResponseEntity<?> register(
        @RequestBody @Valid RegisterRequest request,
        HttpServletResponse httpServletResponse,
        @CookieValue(name = "pendingToken", required = false) String pendingToken
)
```

| Thành phần | Mô tả |
|-----------|-------|
| **Body**  | `RegisterRequest` – chứa `username`, `email`, `password`, `confirmPassword`, `fullName`. |
| **Cookie** (tùy chọn) | `pendingToken` – UUID được lưu ở client để xác định phiên OTP hiện tại (nếu có). |
| **Trả về** | `ResponseEntity.ok(APIResponse.success())` nếu mọi bước thành công; lỗi sẽ được ném ra dưới dạng `AppException` và được `GlobalExceptionHandler` chuyển thành `ErrorResponse`. |

## 2. Các bước nghiệp vụ trong `AuthServiceImplement.register`

### 2.1 Kiểm tra đầu vào cơ bản  

1. **Password vs confirmPassword**  
   ```java
   if (!request.password().trim().equals(request.confirmPassword().trim())) {
       throw new AppException(ErrorCode.PASSWORD_MISMATCH);
   }
   ```

2. **Chuẩn hoá**  
   ```java
   String username = request.username().trim();
   String email    = request.email().trim().toLowerCase();
   ```

### 2.2 Kiểm tra tính duy nhất / tình trạng tài khoản  

| Kiểm tra                                       | Repository / Method                                      | Ý nghĩa                                                                | Exception nếu fails       |
| ---------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------- |
| Email đã được sử dụng bởi tài khoản **active** | `userRepository.isEmailAlreadyInUse(email)`              | Tài khoản có `isActive = true` và `deleted = false`                    | `EMAIL_ALREADY_IN_USE`    |
| Email thuộc tài khoản **bị ban**               | `userRepository.isEmailBanned(email)`                    | Tài khoản có `isActive = true` và `deleted = true` (is_deleted = true) | `ACCOUNT_BANNED`          |
| Username đã được dùng bởi email **khác**       | `userRepository.isUserNameAlreadyInUse(username, email)` | Tồn tại user khác có cùng username nhưng email khác                    | `USERNAME_ALREADY_IN_USE` |

### 2.3 Xử lý tài khoản **chưa active** (tài khoản tồn tại nhưng `isActive = false`)  

- Nếu `userRepository.isInactiveAccount(email)` trả về `true`:  
  1. Tải entity `User` bằng `findByEmail(email)`.  
  2. Cập nhật `username`, `fullName`, `password` (mã hoá bằng `passwordEncoder`).  
  3. Giữ `isActive = false`, `deleted = false` và lưu (`userRepository.save(user)`).  
- Ngược lại (không có bản ghi nào) → tạo mới đối tượng `User` với các trường trên và `isActive = false`, `deleted = false`, sau đó lưu.

> **Lưu ý**: Ở đây tài khoản vẫn **chưa active**; việc kích hoạt sẽ xảy ra sau khi OTP được xác thực thành công (xem API `verify-otp`).

### 2.4 Kiểm tra giới hạn gửi OTP (anti‑spam)  

```java
if (otpService.getAttempts(user.getId()) >= 5) {
    throw new AppException(ErrorCode.OTP_SEND_LIMIT_REACHED);
}
```

- `otpService.getAttempts(userId)` đọc key Redis `otp:attempts:{userId}` (fixed‑window counter trong 1 giờ).  
- Nếu đã đạt **5** lần gửi OTP trong giờ hiện tại → chặn gửi thêm.

### 2.5 Xử lý **cooldown** (ngăn gửi OTP liên tục)  

```java
long cooldownTTl = otpService.getCooldownTtl(user.getId());
if (cooldownTTl > 0) {
    // Đang trong thời gian cooldown → chỉ tái sử dụng / rotate pending token
    String token = resolveOrCreatePendingToken(user.getId(), pendingToken);
    writePendingCookie(response, token);
    return;   // không tạo OTP mới
}
```

- `otpService.getCooldownTtl(userId)` đọc TTL của key `otp:cooldown:{userId}` (60 s).  
- Nếu còn thời gian cooldown → **không** tạo OTP mới, chỉ đảm bảo rằng có một `pendingToken` hợp lệ (được tạo/reused bởi `resolveOrCreatePendingToken`) và ghi cookie này về client, sau đó trả lời thành công ngay.

### 2.6 Xử lý **pending token** (UUID lưu trong cookie)  

- **Hàm `rotatePendingToken(Long id)`**  
  1. Lấy token cũ liên kết với `userId` từ Redis: `pending:user:{id}`.  
  2. Nếu tồn tại → xóa key `pending:{oldToken}`.  
  3. Tạo UUID mới (`newToken`).  
  4. Lưu cả hai hướng:  
     - `pending:{newToken}` → `userId` (string)  
     - `pending:user:{userId}` → `newToken`  
     - Mỗi key có TTL = `PENDING_TTL_MINUTES` (10 phút).  
  5. Trả về `newToken`.  

- **Hàm `resolveOrCreatePendingToken(Long id, String pendingToken)`**  
  1. Ưu tiên lấy token đã map từ `pending:user:{id}` (reverse index).  
  2. Nếu không có hoặc token cũ không khớp với `pendingToken` từ cookie → tạo token mới như ở trên.  
  3. Đảm bảo cả hai hướng đều được lưu / cập nhật TTL.  

- **Ghi cookie** (`writePendingCookie`)  
  ```java
  ResponseCookie.from("pendingToken", token)
                .httpOnly(true)
                .secure(false)   // dev environment; trong prod sẽ true
                .path("/")
                .maxAge(600)     // 10 phút
                .build();
  ```
  Cookie này là **HttpOnly**, không thể truy cập qua JS → phòng chống XSS.

### 2.7 Tạo và gửi OTP  

1. **Tạo OTP**: `String otp = otpService.generateOtp();`  
   - Sử dụng `SecureRandom` để sinh số nguyên từ 0‑999 999, sau đó định dạng thành chuỗi 6 chữ số (ví dụ `042381`).  

2. **Lưu OTP vào Redis**: `otpService.saveOtp(user.getId(), otp);`  
   - Key: `otp:{userId}`  
   - Value: chuỗi OTP  
   - TTL = `OTP_TTL_SECONDS = 300` giây (5 phút).  

3. **Bật cooldown**: `otpService.setCooldown(user.getId());`  
   - Key: `otp:cooldown:{userId}`  
   - Value: `"1"` (marker)  
   - TTL = `COOLDOWN_SECONDS = 60` giây.  

4. **Cập nhật counters**:  
   - `otpService.incrementAttempts(user.getId());`  
     - Key: `otp:attempts:{userId}` – tăng 1; nếu là lần đầu trong cửa sổ 1 giờ thì đặt TTL = 3600 s (fixed‑window).  
   - `otpService.resetWrong(user.getId());`  
     - Đặt `otp:wrong:{userId} = "0"` (TTL 5 phút) để bắt đầu đếm sai mới cho OTP này.  

5. **Gửi email**: `emailService.sendOtpEmail(email, username, otp);`  
   - Sử dụng template HTML `otp.html` (được load từ `classpath:/templates/email/otp.html`).  

### 2.8 Trả lời client  

- Sau khi tất cả thao tác trên thành công, phương thức `register` kết thúc (không ném ngoại lệ).  
- `AuthController` nhận được `void` từ service và trả về:  

  ```java
  return ResponseEntity.ok(APIResponse.success());
  ```

- Cookie `pendingToken` đã được ghi vào response (bước 2.6) → client sẽ gửi lại cookie này trên các request kế tiếp (`verify-otp`, `resend-otp`, `login` khi tài khoản chưa active).

## 3. Tổng quan luồng (biểu đồ trình tự ngắn gọn)

```
Client  -->  POST /api/v1/auth/register  (JSON + optional pendingToken cookie)
          |
          v
AuthController.register
          |
          v
AuthServiceImplement.register
          |
          ├─ Kiểm tra password match
          ├─ Email already active?      --> throw EMAIL_ALREADY_IN_USE
          ├─ Email banned?              --> throw ACCOUNT_BANNED
          ├─ Username already in use?   --> throw USERNAME_ALREADY_IN_USE
          │
          ├─ (Nếu tài khoản inactive)  --> cập nhật/tạo User (isActive=false)
          │
          ├─ Attempt >= 5?              --> throw OTP_SEND_LIMIT_REACHED
          │
          ├─ Cooldown > 0?              --> rotate pending token, write cookie, RETURN
          │
          ├─ rotatePendingToken(userId)  --> tạo/lưu pending token (cookie)
          ├─ writePendingCookie(response, token)
          │
          ├─ generateOtp()
          ├─ saveOtp(userId, otp)        --> Redis key otp:{userId}
          ├─ setCooldown(userId)         --> Redis key otp:cooldown:{userId}
          ├─ incrementAttempts(userId)   --> Redis key otp:attempts:{userId} (fixed‑window)
          ├─ resetWrong(userId)          --> Redis key otp:wrong:{userId}=0
          └─ sendOtpEmail(email, username, otp)
          |
          v
ResponseEntity.ok(APIResponse.success())   + Set‑Cookie: pendingToken=<UUID>
```

## 4. Điểm cần lưu ý khi viết tài liệu cho API này  

- **OTP không lưu ở client** – chỉ tồn tại trong Redis (`otp:{userId}`) với TTL 5 phút.  
- **pendingToken** là UUID HttpOnly cookie, dùng để liên kết client ↔️ phiên OTP (lookup qua `pending:{token}` → userId).  
- **Giới hạn gửi OTP** (attempts) dựa trên **fixed‑window 1 giờ**, không reset mỗi lần increment → giúp ngăn thao tác “mỗi phút gửi 1 lần mãi mãi”.  
- **Cooldown** (60 s) chỉ chặn việc **gửi OTP mới**; trong thời gian này client vẫn có thể verify OTP hiện tại.  
- Nếu người dùng đã có một tài khoản chưa active (`isActive = false`) thì quá trình register sẽ **cập nhật** thông tin (username, fullName, password) và bắt đầu lại luồng OTP – không tạo bản ghi mới trùng lặp.  
- Sau khi OTP được xác thực thành công (API `verify-otp`) thì tài khoản sẽ được set `isActive = true` và tất cả key OTP + pending token sẽ được xóa (`clearAll`).  

Với mô tả trên, bạn có thể viết một phần tài liệu chuyên mục **“Đăng ký tài khoản (Register)”** cho API `/api/v1/auth/register` một cách chi tiết, đủ để các dev bên frontend hoặc bên hiểu rõ những gì xảy ra phía backend khi gọi endpoint này.
